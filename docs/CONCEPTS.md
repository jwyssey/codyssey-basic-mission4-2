# 장애별 OS 개념

## 메모리 누수와 보호 종료

프로세스의 가상 주소 공간에는 코드, 데이터, 힙, 스택 등의 영역이 있다. 메모리를 할당해 쓰고 불필요한 데이터를 계속 보존하면 실제 메모리 소비가 증가할 수 있다. Python에서도 참조를 계속 보관하면 더 이상 필요하지 않은 데이터가 회수되지 않을 수 있다. 그러나 이 앱의 구체적인 참조 구조는 제공 소스 없이 확인할 수 없다.

가상 주소 공간 크기(VMS)와 실제 상주 메모리(RSS)를 구분해 관찰한다. 물리 메모리 부족이 커지면 다른 프로세스도 메모리 회수·스왑 등의 영향을 받을 수 있지만, 이번 앱의 MemoryGuard는 커널 전체 메모리 고갈 전에 자체 상한으로 종료할 수 있다. 임계값 상향은 생존 시간 연장 여부를 확인하는 임시 조치다.

## CPU 과점유와 지연

CPU에서 실행할 수 있는 작업 수는 제한되어 있다. 연산 작업이 CPU를 오래 점유하면 같은 CPU를 기다리는 다른 작업의 실행이 늦어질 수 있다. CPU 사용률, 실행 대기, 응답시간은 서로 관련되지만 같은 지표는 아니다. 이 과제는 우선 대상 프로세스의 급상승과 보호 종료 정책을 증명한다.

한 프로세스가 논리 CPU 한 개를 지속적으로 사용해도 다수 CPU를 가진 시스템의 전체 평균은 작게 보일 수 있다. 과제 1은 시스템 전체 CPU/MEM을 수집했고, 과제 2 도구는 PID별로 수집하는 이유다.

## 교착상태와 단순 대기

서로 다른 스레드가 자원을 보유한 상태에서 상대방의 자원을 무기한 기다리면 작업 진행이 막힐 수 있다. 식사하는 철학자 비유에서 각 철학자가 왼쪽 포크를 들고 오른쪽 포크를 기다리는 상황이 순환 대기를 설명한다. 상호 배제·점유 대기·비선점·순환 대기의 네 조건을 함께 검토한다.

락 대기 시 스레드는 CPU를 계속 소비하는 대신 잠들 수 있다. PID는 존재하고 RSS도 유지되지만 처리량과 로그 진행이 멈추는 패턴이 가능하다. 다만 이것은 정상적인 요청 대기에서도 보일 수 있어 마지막 로그의 락 획득·대기 관계가 중요하다. [Python Lock 설명](https://docs.python.org/3/library/threading.html#lock-objects)은 이미 잠긴 락의 acquire가 해제까지 대기하는 동작을 정의한다.

## 보너스: 스케줄링 추론의 범위

실제 작업 로그에서 A→B→C 순환, Preempted/Resumed 및 진행률 보존을 확인했다. [보너스 분석 보고서](../reports/04-scheduling.md)에 이벤트 시각과 약 153~155 ms의 초기 교대 간격을 정리했다. 결론은 앱 수준 Round-Robin 패턴이며 커널 정책을 확정한 것은 아니다.

| 후보 | 확인할 패턴 | 장점과 한계 |
| --- | --- | --- |
| FCFS | 도착 순서대로 하나의 작업이 끝난 뒤 다음 작업 진행 | 단순하지만 긴 작업 뒤에 짧은 작업이 오래 기다릴 수 있음 |
| Round-Robin | 실행 가능한 작업들이 일정한 시간 할당을 번갈아 사용 | 응답 기회를 나누기 좋지만 교체 비용·할당 시간 선택이 중요 |
| Priority | 우선순위가 높은 작업에 실행 기회가 우선 배정 | 중요한 작업 지연을 줄이지만 낮은 우선순위의 기아 가능 |

로그가 A→B→C→A 순서라는 사실만으로 OS가 Round-Robin을 사용한다고 확정할 수 없다. 앱의 sleep, I/O, 런타임 락, 로그 버퍼링도 순서에 영향을 준다. 선점처럼 보이는 로그가 있으면 단순한 비선점 FCFS와 맞지 않는다는 가설을 세울 수 있지만, 실제 스케줄러 정책은 추가 증거가 필요하다.

Linux의 `SCHED_RR`은 특정 실시간 정책이므로 일반 앱의 로그 교대 패턴과 동일시하지 않는다. 확인 가능한 환경에서는 `chrt -p PID`, `ps -o pid,cls,rtprio,pri,ni -p PID`로 정책을 조회하고 앱 수준 작업 배분과 구분해 기술한다. 정책은 변경하지 않는다. [sched(7)](https://man7.org/linux/man-pages/man7/sched.7.html)
